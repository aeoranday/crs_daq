# Charge Readout System Data Acquisition
This is the Deep Underground Neutrino Experiment (DUNE) Near Detector's (ND) Charge Readout System (CRS) Data Acquisition (DAQ) framework. This is accompanied by the [`larpix-control`](https://github.com/larpix/larpix-control) package in order to control the hardware components of the CRS.

## Configuration
The system uses a top-level configuration file `configs/RUN_CONFIG.json` and supplementary configuration files at both a mid-level and low-level which are generated and modified by scripts within this repository.

## Example Workflow
The first step is to configure the PACMAN board. Within a Python environment with `crs_daq`,
```bash
python scripts/configure_pacman.py --pacman-config configs/io/pacman_iog1.json
```
to configure one IO group (in this case IO group 1), or
```bash
python scripts/configure_pacman.py
```
to configure using the contents of `configs/io/pacman.json`. The `configs/io/pacman.json` file can be modified to produce the same effect as the first command and options.
This script applies a configuration to the PACMAN board that would:
* Power the board,
* Set the clock,
* Set the VDDA and VDDD,
* Reset chips on the board,
* Enable charge readout tiles.

To confirm the effectiveness of the configuration, the voltages and currents per tile can be shown using
```bash
python scripts/monitor_power.py
```
One would expect an IDDD of approximately 500 mA.

The next step is to create a "hydra" network between the chips on the charge readout tile.
To generate this network, run
```bash
python scripts/hydra_v3.py --io-group 1
```
In the case of only one tile, one can use the additional flag `--pacman-tile <n>`.
This script:
* Resets the tiles,
* Tries to establishes a communication between neighboring chips,
* Find working communication links,
* Identifies "root" chips (chips that can be root nodes to the chip network),
* Saves the chip network graph to PNG files,
* Saves the representative network config JSON.

An example chip network is the following:
![chip-network](configs/iog_1-tile_1-hydra-network.png)
In this case, the blue squares indicate root chips and the red square is a chip that failed to communicate.

Now that the chip network is established, we may initialize it using
```bash
python scripts/network_larpix.py --controller-config configs/controller_config.json
```
The `controller_config.json` is another high-level configuration file that references a mid-level JSON, e.g., `configs/config-io_group-1.json`, which further links the lower-level chip network configuration files, e.g., `configs/iog_1-tile_1-hydra-network.json`. Since the mid-level `config-io_group-1.json` specifies the chip network configuration files, the mid-level JSON's contents must match the user's expected chip network configuration path. This can be done by modifying the mid-level JSON or using the same path and name for the low-level chip network JSON.
The script then
* Reads the chip network JSON files, as in `configs/config-io_group-1.json`,
* Builds the controller network,
* Initializes the chips to a default state,
* Enforces configuration application iteratively,
* Writes ASIC configuration files to `asic_configs` with a current timestamp.

The network initialization can fail. Such is the case when the tiles are producing data packets at a high rate. One can do the traditional turn-off/turn-on sequence using
```bash
python scripts/power_down_larpix.py
```
and repeating the previous steps. If a chip continues to fail, it can be excluded by inserting it into the `iog_exclude_links` field in `configs/RUN_CONFIG.json`.

At this point, the system is ready for data taking. In our example, we will take a pedestal-focused data run. Our base ASIC configuration can be preserved by copying into a new path for modification:
```bash
cp -r asic_configs/<timestamped_config_dir> asic_configs/pedestal_example
```
where the `<timestamped_config_dir>` is the set of configs generated by `network_larpix.py`.
Then mutate the copied configs with
```bash
python scripts/generate_pedestal_config.py asic_configs/pedestal_example/*
```
Then enable the CSA and disable channel masking with
```bash
python scripts/enable_csa_disable_channel_mask.py asic_configs/pedestal_example/*
```
We can then set a periodic trigger using
```bash
python scripts/write_register_to_config.py asic_configs/pedestal_example/* --register periodic_trigger_cycles --value 10000
```
where each cycle is is 100 ns.
To apply these configurations to the hardware,
```bash
python scripts/configure_larpix.py --asic-config asic_configs/pedestal_example
```
To record data,
```bash
python scripts/record_data.py --packet --runtime 60 --file-count 1
```

To check the results of this pedestal run,
```bash
python scripts/analysis/plot_metric.py --filename <saved_filename>.h5
```
